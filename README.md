# Product API Assessment

Clean-architecture ASP.NET Core Web API targeting .NET 8. The solution uses JWT bearer authentication, role-based authorization, Entity Framework Core with SQL Server, repository and unit-of-work abstractions, Serilog logging, Swagger/OpenAPI, and layered automated tests.

## Repository Structure

| Project | Responsibility |
| --- | --- |
| `src/API` | HTTP API, controllers, middleware, configuration, authentication, and Swagger |
| `src/Application` | Application services, DTOs, validation, interfaces, and mapping |
| `src/Domain` | Domain entities and shared domain abstractions |
| `src/Infrastructure` | EF Core context, migrations, repositories, unit of work, and data seeding |
| `tests` | API, application, and infrastructure tests |

# Documentation

## 1. OpenAPI / Swagger Documentation

The API uses Swashbuckle.AspNetCore to generate an OpenAPI document and serve Swagger UI. Swagger is enabled by default through the `EnableSwagger` configuration setting and can be disabled by setting it to `false`.

### Local URLs

The development launch profiles expose:

```text
http://localhost:5024/swagger/index.html
https://localhost:7237/swagger/index.html
```

The generated OpenAPI JSON is available at:

```text
/swagger/v1/swagger.json
```

Start the API from the repository root with:

```bash
dotnet run --project src/API/API.csproj
```

Swagger is also available when running the supplied Docker Compose configuration at:

```text
http://localhost:5000/swagger/index.html
```

### Swagger Authentication

Swagger registers an HTTP bearer security scheme for JWTs. To call protected operations:

1. Obtain an access token through `POST /api/v1/auth/login`.
2. Select **Authorize** in Swagger UI.
3. Enter the token using the bearer format requested by the dialog.

The API then sends the token in the `Authorization` header. Swagger is configured to persist authorization state in the UI for the current browser session.

### API Areas

The API uses URL versioning with version `1.0` and currently exposes:

- `AuthController` at `/api/v1/auth` for login, refresh, logout, and the current-user endpoint.
- `ProductsController` at `/api/v1/products` for product reads and Admin-only product mutations.
- `ItemsController` at `/api/v1/products/{productId}/items` for item reads and Admin-only item mutations.

## 2. Code Documentation

The project does not currently use hand-written C# XML documentation comments, JSDoc, or Swashbuckle annotation attributes such as `SwaggerOperation`.

The API uses framework metadata and attributes to describe endpoints, including:

- `[ApiController]`, HTTP method attributes, and API version attributes.
- `[ProducesResponseType]` for response status and DTO metadata.
- `[Consumes]` for request content types.
- Swagger configuration in `src/API/Extensions/ServiceCollectionExtensions.cs` for the API title, version, description, and bearer security scheme.

Swagger conditionally calls `IncludeXmlComments` when an API XML documentation file exists. XML documentation generation is not enabled in the current project file, so application XML comments are not currently included in the generated OpenAPI document. EF Core generated migration files may contain compiler-generated `inheritdoc` comments, but these are not the project's API documentation convention.

## 3. Authentication & Authorization Flow

The API separates authentication from authorization:

- **Authentication** verifies who the caller is by validating a JWT bearer token.
- **Authorization** determines whether the authenticated caller has permission to execute an endpoint, including role checks.

The implemented flow is:

```text
Client
  -> POST /api/v1/auth/login
  -> AuthService validates the user, active status, and password hash
  -> JwtTokenService generates an access token and refresh token
  -> Client sends Authorization: Bearer <access-token>
  -> JwtBearer middleware validates signature, issuer, audience, and lifetime
  -> Claims and role are made available to ASP.NET Core authorization
  -> [Authorize] or [Authorize(Roles = "Admin")] is evaluated
  -> Controller
  -> Application service
  -> Repository/unit of work
  -> SQL Server database
```

### JWT Claims

Access tokens generated by the application include:

- User identifier
- Username
- Email
- Role
- JWT ID (`jti`)

The token is signed with the configured JWT secret. Configure that secret outside source control; do not use a repository default in production.

### Roles and Endpoint Access

The application currently uses the `User` and `Admin` roles.

| Area | Access |
| --- | --- |
| `POST /api/v1/auth/login` | Anonymous |
| `POST /api/v1/auth/refresh` | Anonymous |
| `POST /api/v1/auth/logout` | Authenticated users |
| `GET /api/v1/auth/me` | Authenticated users |
| Product read endpoints | Authenticated users |
| Product create, update, and delete endpoints | `Admin` role |
| Item read endpoints | Authenticated users |
| Item create, update, and delete endpoints | `Admin` role |

Authentication is configured with JWT bearer middleware. The request pipeline runs routing, authentication, authorization, and then controller endpoint handling in that order. There are no custom authorization policies; controller attributes provide the current role checks.

## 4. Environment Setup

### Prerequisites

- .NET 8 SDK
- SQL Server, or Docker Desktop when using the supplied Docker Compose configuration
- `dotnet-ef` global tool for running EF Core commands manually

Install the EF Core CLI tool if it is not already installed:

```bash
dotnet tool install --global dotnet-ef
```

### Configuration

ASP.NET Core loads configuration from `src/API/appsettings.json`, environment-specific settings such as `appsettings.Development.json`, and environment variables. No `.env` file or user-secrets configuration is defined in the repository.

Provide the following values through deployment configuration or environment variables:

| Configuration key | Environment variable | Purpose |
| --- | --- | --- |
| `ConnectionStrings:SqlServer` | `ConnectionStrings__SqlServer` | SQL Server connection string |
| `JwtSettings:Issuer` | `JwtSettings__Issuer` | JWT issuer |
| `JwtSettings:Audience` | `JwtSettings__Audience` | JWT audience |
| `JwtSettings:SecretKey` | `JwtSettings__SecretKey` | At least 32 characters; keep secret |
| `JwtSettings:AccessTokenExpirationMinutes` | `JwtSettings__AccessTokenExpirationMinutes` | Access-token lifetime |
| `JwtSettings:RefreshTokenExpirationDays` | `JwtSettings__RefreshTokenExpirationDays` | Refresh-token lifetime |
| `SeedUsers:AdminPassword` | `SeedUsers__AdminPassword` | Initial Admin seed password |
| `SeedUsers:UserPassword` | `SeedUsers__UserPassword` | Initial User seed password |
| `EnableSwagger` | `EnableSwagger` | Enable or disable Swagger |
| `UseHttpsRedirection` | `UseHttpsRedirection` | Enable HTTPS redirection |
| `SkipDatabaseInitialization` | `SkipDatabaseInitialization` | Skip startup migration and seeding when explicitly required |

Example environment variable values should use placeholders and a deployment-specific secret:

```text
ConnectionStrings__SqlServer=<YOUR_CONNECTION_STRING>
JwtSettings__Issuer=<YOUR_JWT_ISSUER>
JwtSettings__Audience=<YOUR_JWT_AUDIENCE>
JwtSettings__SecretKey=<YOUR_JWT_SECRET_AT_LEAST_32_CHARACTERS>
JwtSettings__AccessTokenExpirationMinutes=60
JwtSettings__RefreshTokenExpirationDays=7
```

The Testing environment uses an in-memory EF Core database, disables database initialization, and disables Swagger by default. The API test host explicitly enables Swagger for Swagger integration tests.

### Database Setup

The API uses EF Core SQL Server migrations. From the repository root, apply existing migrations with:

```bash
dotnet ef database update \
  --project src/Infrastructure/Infrastructure.csproj \
  --startup-project src/API/API.csproj \
  --context ApplicationDbContext
```

Create a new migration with:

```bash
dotnet ef migrations add <MigrationName> \
  --project src/Infrastructure/Infrastructure.csproj \
  --startup-project src/API/API.csproj \
  --context ApplicationDbContext
```

Outside the Testing environment, application startup applies migrations and seeds product, item, and user data unless `SkipDatabaseInitialization` is set to `true`.

### Run the Application

Restore and run from the repository root:

```bash
dotnet restore ProductApiAssessment.sln
dotnet run --project src/API/API.csproj
```

The launch profiles set `ASPNETCORE_ENVIRONMENT=Development` and use:

- `http://localhost:5024`
- `https://localhost:7237`

The HTTPS profile may require trusting the local ASP.NET Core development certificate.

### Tests

Run the full test suite with:

```bash
dotnet test ProductApiAssessment.sln
```

Individual test projects are available under `tests/API.Tests`, `tests/Application.Tests`, and `tests/Infrastructure.Tests`.

## 5. Deployment

### Published Application

The repository includes a manual .NET publish workflow:

```bash
dotnet publish src/API/API.csproj -c Release -o ./publish
cd publish
dotnet API.dll
```

Production configuration must provide a reachable SQL Server connection, a strong JWT secret, issuer and audience values, token lifetimes, and appropriate values for `EnableSwagger`, `UseHttpsRedirection`, and `SkipDatabaseInitialization`. Use a secret manager or deployment environment variables for sensitive values.

The application runs EF Core migrations and data seeding during startup by default. Confirm database permissions and migration strategy before deploying multiple instances or applying migrations in a separate release step.

### Container Deployment

The repository contains a multi-stage `Dockerfile` targeting the .NET 8 SDK and ASP.NET runtime images. Build the image from the repository root:

```bash
docker build -t productapiassessment:latest .
```

The container listens on port `80`. Run it with deployment-provided configuration, for example:

```bash
docker run -d -p 5000:80 \
  -e ConnectionStrings__SqlServer=<YOUR_CONNECTION_STRING> \
  -e JwtSettings__Issuer=<YOUR_JWT_ISSUER> \
  -e JwtSettings__Audience=<YOUR_JWT_AUDIENCE> \
  -e JwtSettings__SecretKey=<YOUR_JWT_SECRET> \
  productapiassessment:latest
```

The supplied `docker-compose.yml` starts SQL Server and the API for local development/testing. It exposes SQL Server on port `1433` and the API on port `5000`; replace its development credentials and secrets before using any equivalent configuration outside a local environment.

### CI/CD

No GitHub Actions workflow, cloud deployment configuration, or automated CI/CD pipeline is currently present in the repository. Builds, tests, publishing, and container deployment are therefore manual unless an external pipeline is added.
